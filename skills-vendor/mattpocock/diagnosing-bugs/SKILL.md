# Diagnosing Bugs

先检查相关代码、项目领域资料与 ADR，确认用户描述的症状和当前环境。命令、日志、请求和捕获文件中的凭证先脱敏，只展示诊断所需内容。

## 建立可验证的复现

选择能观察真实故障路径的反馈方式：失败测试、HTTP/CLI 请求、浏览器操作、真实轨迹重放、最小 harness、属性/压力测试或版本差分。人工步骤无法消除时使用 `scripts/hitl-loop.template.sh`。优先让反馈快速、稳定且可重复，不为建立 harness 延迟必要的代码检查。

至少运行一次并记录触发条件、准确症状和结果。反馈必须能识别用户报告的问题，不能只检查没有崩溃。间歇性问题记录触发率和负载条件；性能问题先测基线再优化，控制资源需求。

逐步缩小复现，每次只减少一个相关因素，并确认症状仍存在。无法复现时说明尝试和证据缺口；仍可从代码或日志排查，但将原因标为假设，不宣称已经验证。需要额外环境或生产探针时说明具体需求及授权范围。

## 用证据区分原因

针对现有证据提出有竞争力的假设，写明每个假设的可检验预测，不凑固定数量。先检查最能区分候选原因的变量。

可用时使用调试器或 REPL，其次添加边界日志；每个探针对应一个预测，每次只改变一个变量。临时日志用唯一前缀标记，不收集无关敏感数据。性能退化优先使用 profiler、查询计划或差分测量。

## 修复与验收

在能覆盖真实调用模式的边界保留回归验证，条件允许时先观察其失败再修复。测试不得通过复制实现或过浅的 mock 制造通过。

修复根因后重跑原始场景及相关检查。没有可用回归边界时说明限制，不用无效测试代替证据。

清理本次添加的临时日志和 harness，保留必要复现证据。交付说明根因、修复及实际验证结果，未复现或未验证的部分分别标明。
