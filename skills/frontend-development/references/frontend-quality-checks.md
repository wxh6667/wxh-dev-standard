# Frontend Quality Checks

仅在页面涉及接口数据、复杂交互、共享状态或 UI 一致性时按需读取。简单静态修改不要为了检查表扩大范围。

## 数据契约优先

先确认接口返回结构、字段可空性、错误语义和已有类型定义，再实现依赖这些数据的 UI。不要通过猜测字段、伪造默认值或静默兜底掩盖契约问题。

## 页面状态

数据驱动页面至少根据实际业务考虑 loading、error、empty 和正常状态；是否需要额外 disabled/submitting/partial 等状态由交互决定。异常或空数据应进入明确状态，不伪装成成功内容。

## 组件与样式

优先使用项目已有组件库、设计 token 和相邻页面模式。展示与数据/副作用逻辑只在确实有复杂度时拆分；不要因为固定行数阈值机械拆文件，也不要为了“可复用”提前造抽象。

## 状态归属

同一份事实尽量只有一个来源。服务端数据使用项目现有的数据获取/缓存方案；全局 UI 状态进入已有全局 store；局部交互状态留在组件附近；分页、筛选、tab 等如果项目已有 URL 状态约定，沿用该约定。不要重复复制同一数据到多个 store/state。

## 实现输入

复杂页面优先收集实际设计参考、现有组件库、数据契约、交互流程和关键边界场景。已有项目能从代码和相邻页面推断的内容直接读取，不要求用户重复提供。

## 完成检查

验证页面真实构建和关键交互，重点检查类型/契约、加载与失败路径、空状态、权限可见性、状态重复、样式是否偏离现有设计系统，以及是否为了修一个页面新增了不必要的全局抽象。
