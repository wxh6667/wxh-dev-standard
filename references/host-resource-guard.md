# Host Resource Guard

这是跨机器通用的重任务资源保护规则，不绑定某一台旧主机，也不固定某个 cgroup、builder 或 CPU 配额。

## 核心要求

执行 Maven/Gradle、大型前端构建、本地完整测试集、本地 Docker 构建或其它明显吃内存的任务前，先检查主机当前可用内存。Linux 优先参考 `/proc/meminfo` 中的 `MemAvailable` 或 `free -h` 的 `available`，不要只看 `free` 字段。

**主机必须保留至少约 2 GiB 的可用内存安全余量。** 这 2 GiB 是留给操作系统、Agent、SSH、数据库、容器和其它常驻服务的，不是“构建任务最多只能使用 2 GiB”。

执行重任务时，应先根据当前 `MemAvailable` 计算本次任务可以安全使用的资源空间。原则上，可供本次重任务消耗的内存上限不能把主机剩余可用内存压到 2 GiB 安全线以下。

如果当前可用内存本身已经接近或低于 2 GiB，或者按当前服务占用和任务规模判断无法守住 2 GiB 安全线：

1. 不直接启动高内存任务；
2. 优先降低 Maven/Gradle/测试并发和 JVM/Node 等进程的可用内存；
3. 可以安全释放临时进程、缓存或无用构建资源时再释放；
4. 当前 Linux 环境确实需要硬限制时，可以根据实时可用内存动态使用 cgroup/systemd-run 等限制任务，而不是写死历史配额；
5. 生产 Docker 镜像按本仓库规则走 CNB 远程构建，不为了本机构建去挤占主机内存；
6. 不得擅自停止数据库、生产容器或其它业务服务来腾内存；
7. 无法保证至少约 2 GiB 主机余量时，停止该重任务并明确报告资源不足。

## 旧策略如何理解

旧环境中的 Maven `systemd-run` 2 CPU / 2 GiB，以及 `codex-limited` Docker builder 3 GiB / 2 CPU，是特定机器上为了保护主机资源采用的实现手段，不是需要原样复制到所有机器的固定标准。

现在保留的是它们背后的真实约束：**无论机器总内存是多少，重任务不能把主机可用内存吃到低于约 2 GiB。** CPU 数量、JVM 内存、测试并发、cgroup MemoryMax 或 builder 限额应根据当前主机实时资源和任务类型动态决定。
