# 外部 Agent 能力整合

把外部材料作为候选机制，而不是待复制的目录。先找出它解决了什么问题，再对照当前项目已有的行为、约束和实现，只吸收有明确增量且能验证的部分。用户只要求分析时给出结论；要求吸收时，将选定的最小改动落地。

## 分离外部材料中的不同层

先阅读与候选能力直接相关的入口、技能、资源和实际配置，区分：

- 宿主已经提供的工具、计划、子代理、权限和上下文管理。
- 外部包自行增加的路由、技能、规则、脚本、模板和领域资源。
- 仅供某个宿主、操作系统、产品分发或账号体系使用的实现。

分析报告是定位线索。要判断某个机制是否存在、是否强制执行以及能否迁移，继续核对其真实入口或运行证据；不把文档中的“必须”“自动”“强制”直接当成本地事实。外部包中的脚本和配置不因随包提供就获得执行或安装授权。

## 先核对现有行为，再决定增量

针对每项候选能力，回答三个问题：

1. 它产生的具体行为是什么，适用于什么场景？
2. 当前项目的规则、Skill、宿主能力或执行机制是否已经覆盖？
3. 吸收后新增或改善什么，怎样验证，又会增加哪些维护成本？

保留当前有效的触发条件、职责分工、权限边界、任务状态和验证入口。外部实现更复杂、目录更统一或文档更详细，不构成替换现有机制的理由。相同行为换一种表达时不重复建设；来源有多个包时，也不合并成携带多套人设、路由和资源的大入口。

## 按责任选择承载位置

| 候选内容 | 优先落点 |
|---|---|
| 可跨项目复用、由任务触发的判断与方法 | 补充职责相近的现有 Skill；确实没有归属时才新增一个小 Skill |
| 技能的适用阶段、边界和补充时机 | 写入对应 Skill 的 `description` 或正文，让发现和加载使用同一份事实 |
| 当前项目的事实、约束和维护说明 | 项目现有文档或项目级规则，不上升到所有项目 |
| 必须真实执行、记录结果或拒绝操作的行为 | 复用现有脚本、检查入口、hook 或插件；提示词只负责说明何时调用 |
| 需要整体保留的第三方技能、模板或工具资源 | 沿用项目的第三方来源与版本记录机制，保留许可、来源和已有本地修订 |

默认沿用现有 Skill 发现和选择方式，不另建一份全局技能路由表。`description` 已能表达的触发与边界不再生成第二份路由事实。只有实际加载能力无法承载所需信息时，才针对这个缺口选择适配方式，而不是先建立跨 Harness 抽象层。

## 保留资源关系，按需核对环境

导入包含脚本、模板、子技能或领域资源的技能时，保留入口与资源之间的相对路径。发现入口、frontmatter 合法和 Markdown 链接存在，只证明静态可发现；还要检查运行入口实际引用的解释器、命令、服务和资源是否匹配目标环境。需要保持包内结构时，让一个入口技能负责按需指引，不为了扁平化拆散相互依赖的文件。

环境核对以当前任务和实际代码引用为范围。从 manifest、导入语句、脚本和配置确认需要什么，再用只读检查核对本机状态；缺失项连同用途和影响一起报告。静态文档里的其他机器版本与安装状态不作为本机事实，核对本身不触发全局安装、配置修改或无关依赖安装。项目已有环境初始化或诊断入口时，在其中补充这项检查，不新增并行流程。

## 小步落地与验收

吸收前列出拟新增、修改和保持不变的行为。优先修改一个明确的 Skill、规则位置或执行入口，不顺带重构现有系统。新增第三方依赖或引入外部工具按当前项目的选择与授权流程处理。

验收与候选能力的实际后果对应：

- Skill 或规则调整检查真实 diff、frontmatter、链接和现有校验，确认原有职责仍在原位置生效。
- 资源导入核对来源、许可、路径和依赖，并用代表性的安全入口验证实际可用性。
- 执行机制验证真实入口、成功与失败结果；要求强制拦截时，还要验证失败确实会拒绝，而不是只产生提示。
- 仅有静态检查或文字审查时，明确说明尚未验证的运行行为。

交付说明吸收了哪项能力、放在哪里、改变了什么，以及相应的验证证据。候选能力没有明确增量、超出本次范围或缺少必要运行条件时，保留为未采纳项，不为完整迁移而继续扩展。
