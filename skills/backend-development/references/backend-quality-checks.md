# Backend Quality Checks

仅在后端任务涉及写入、授权、并发、外部副作用、性能或高风险数据边界时按需读取；普通 CRUD 不需要机械套全部检查。

## 先确认不变量

实现前明确本次变更真正相关的不变量：重复请求是否允许、是否要求幂等、哪些写入必须原子完成、唯一性/引用完整性/状态流转由哪里保证。不要为了“保险”同时在多个层复制同一约束。

## 风险分级

只读接口重点检查契约、输入和可观测性。普通写入增加资源级授权与基本测试。支付、扣费、关键状态变更、LLM/第三方调用等外部副作用需要进一步检查幂等键、事务边界、重试语义和失败恢复。

## 授权与数据正确性

权限不能只验证“已登录”，还要验证当前主体是否允许操作目标资源。数据库约束、事务、唯一键和状态机应表达真实业务不变量；不要依赖前端或偶然执行顺序维持数据正确性。

## 可观测性

当故障无法从现有日志定位时，再补真正需要的 request/correlation id、关键业务字段、数据库/外部调用耗时和明确错误。不要为了规范而给所有接口增加无意义日志。

## 慢 SQL

先确认慢的是哪个请求以及数据库耗时占比，再定位具体 SQL。优先检查 N+1、缺索引、不合理 join/order、深 offset 分页和扫描范围；通常先修查询和索引，再考虑缓存，最后才考虑架构改造。

## LLM / 外部调用

涉及计费或长耗时调用时，明确超时、重试、重复扣费、客户端断开、部分结果、成功完成定义以及 token/费用归因。依赖失败默认显式失败，除非产品需求明确允许降级。

## 完成检查

完成条件以本次风险为准，通常至少包括：契约没有意外漂移、输入校验正确、资源授权正确、事务/幂等符合业务、失败可观察、代表性成功与失败路径已验证。不要为满足检查表而制造无关改动。
